# Database migration policy

`PostgresSchema.EnsureAsync` applies the consolidated idempotent baseline and records `001_baseline` in `schema_migrations`. It is safe to execute repeatedly and is tested twice in the same database by CI.

Applied role-foundation migrations:

- `002_role_position_foundation`: creates the canonical `system_roles` and `hr_job_positions` catalogs,
  normalizes legacy role spellings, records changed primary roles in `user_role_history`, adds role foreign
  keys, and links existing employee profiles where possible. It preserves accounts, profiles, sessions, and
  business data; unknown legacy roles fail closed to `Employee` rather than being deleted.
- `003_expand_job_position_catalog`: adds the read-only, company-wide `Executive` role and seeds the
  comprehensive Vietnamese job-position catalog. A director is deliberately not an `Admin`.
- `004_employee_multiple_positions`: creates `hr_employee_positions` (`employee_id`, `position_id`,
  `is_primary`, assignment metadata), backfills the former single `position_id`, enforces one unique
  employee/position pair and at most one primary position. `hr_employees.position_id` remains the
  backward-compatible primary-position field.
- `005_expand_job_position_catalog_2`: adds common board, C-level, branch, specialist-accounting,
  recruiting/C&B, logistics, R&D, occupational-safety, and canteen positions.
- `006_backfill_roles_to_employee_positions`: converts every existing primary and still-active secondary
  account role into a deterministic matching job-position assignment. This prevents legacy multi-role
  access from disappearing when positions become the authorization source of truth; expired temporary
  grants are deliberately not made permanent.
- `007_correct_canonical_role_positions`: forward-corrects only assignments generated by migration 006
  to the explicit generic position for each role (`Employee→EMPLOYEE`, `Executive→BOARD_MANAGEMENT`,
  and equivalent mappings). Assignments already present from migration 004 are not changed.

All migrations run transactionally from `HrEndpoints.EnsureTables`, after the HR baseline tables exist.
They never reset account data. A production rollout still requires a verified backup and at least one
configured bootstrap Admin (`Bootstrap:AdminUsername` / `Bootstrap:AdminPassword`) before migration.

For every later schema change:

1. Assign the next immutable version (`008_...`, and so on).
2. Make the SQL transactional and forward-compatible with the currently deployed API.
3. Insert its version only after the SQL succeeds.
4. Add an integration test that upgrades a baseline database twice and verifies both data preservation and idempotency.
5. Back up and run a restore drill before production deployment.
6. Prefer forward fixes. For a binary rollback, restore the verified pre-deployment dump into a new database and switch the connection secret.

Never edit an already-applied migration version. Never put credentials or sensitive row contents in migration output.
